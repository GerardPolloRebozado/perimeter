# Spike 2 notes: Cassandra + Spring Data Cassandra

**Code:** this directory, which started as a copy of [`../java-spring/`](../java-spring/)

## Timebox

**3 hours, agreed by the whole team before any code was written — the full target was reached inside it.** Docker consumed the biggest single slice: image pull plus ~75 s until the node was ready and the schema applied. Even so, when the timer rang we had `:8080/ping` (both the 200 case and the 503-when-Cassandra-is-down variant), the workflow CRUD endpoints working against the two tables, and 3 tests passing. The remaining minutes went into `schema.cql` and this file.

## What was built

| File | Role |
|---|---|
| `docker-compose.yml` | Project `spike2-cassandra`: `cassandra:5.0` with a small heap (8 GB machine), a healthcheck, and a one-shot `cassandra-init` container that applies the schema. Volume `spike2-cassandra-data`. Host port configurable with `CASSANDRA_PORT` (default 9042) |
| `schema/schema.cql` | Keyspace `surface_volume` + **two tables holding the same workflow data**: `workflows_by_user` (partition key `user_id`) and `workflows_by_action_service` (partition key `action_service`) |
| `build.gradle.kts` | + `spring-boot-starter-data-cassandra` |
| `application.properties` | `PORT` (no default), contact point `${CASSANDRA_HOST:127.0.0.1}:${CASSANDRA_PORT:9042}`, datacenter `datacenter1`, keyspace `surface_volume`, `schema-action=none` (the schema belongs to `schema.cql`) |
| `PingController.java` | Runs `SELECT release_version FROM system.local` → **200** `{"status":"ok"}`, or **503** `{"status":"error"}` if Cassandra doesn't answer |
| `workflow/WorkflowByUser.java`, `WorkflowByActionService.java` | Entities (records) for the two tables |
| `workflow/*Repository.java` | Spring Data repositories. `findByUserId` / `findByActionService` become CQL generated by Spring. |
| `workflow/WorkflowService.java` | `create()` writes **both tables in one logged batch**. Action/reaction configs are stored as **JSON text**. |
| `workflow/WorkflowController.java` | `POST /workflows`, `GET /users/{userId}/workflows`, `GET /services/{service}/workflows` |
| `src/test/.../PingControllerTest.java` | `CqlSession` mocked: ok case, 503 case, CORS |

## How to run it

```sh
cd spikes/2/cassandra
docker compose up -d               # ~75 s until the schema is created (watch: docker compose ps)
./gradlew test                     # 3 tests, no Cassandra needed
PORT=8080 ./gradlew bootRun

curl localhost:8080/ping
curl -X POST localhost:8080/workflows -H 'Content-Type: application/json' -d '{
  "userId":"11111111-1111-1111-1111-111111111111","name":"Star repo -> Discord",
  "actionService":"github","actionType":"new_star","actionConfig":{"repo":"surface-volume/surface-volume"},
  "reactionService":"discord","reactionType":"send_message","reactionConfig":{"channel":"general"}}'
curl localhost:8080/users/11111111-1111-1111-1111-111111111111/workflows
curl localhost:8080/services/github/workflows

docker compose stop                # free ~1.7 GB RAM (data kept)
docker compose down -v             # delete everything, including data
```

## Observations

- **Relational integrity:** none. The same workflow lives in two tables, and keeping them in sync is **our job** (the batch in `WorkflowService`). Nothing stops a deleted user from still having workflows. Update and delete would need the same double-write, which wasn't built.
- **Query flexibility:** only by key. `SELECT … WHERE reaction_service = 'discord'` → *"Cannot execute this query as it might involve data filtering… use ALLOW FILTERING"*. Every new question Surface Volume asks means a new table, or a secondary index with its own trade-offs.
- **JSON storage:** works, but only as **opaque text**. Cassandra can't query inside the config. Fine for "load the workflow and run it", useless for "find workflows whose config mentions repo X".
- **Developer velocity:** the Spring Data layer is pleasant (repositories, records). Cassandra modelling is the slow part: you design tables per query up front.
- **Operations:** ~76 s to be ready, ~1.7 GB RAM for one node, and the app can't start without it. Heavier than a typical SQL container for a project this size.
- **Resilience:** good once connected. The driver reconnects by itself when the node comes back.
- **What Cassandra is great at**, massive write throughput across many nodes. Is this something Surface Volume needs?
